# 07 shelf-spec (ранее openshelf) — роадмап

Порядок фаз зафиксирован владельцем 2026-07-15: **спек и переносимость
вперёд, мульти-агентность вторым слоем** — дизайн при этом закладывает
мульти-агентное ядро с M0 (формат `agents.yml`, provenance-поля в спеке
зарезервированы сразу).

## M0 — спек и переносимость

Извлечь формат из работающих полок, доказать переносимость.

- shelf-spec v0: `SPEC.md` + JSON-схема `shelf.yml`; описывает раскладку,
  frontmatter, INDEX/meta/ledger/POLICY, нормативные правила (recalled =
  данные; INDEX не правится руками; транскрипты не коммитятся).
- `engine/` + тонкие MCP/CLI: `shelf_init`, `shelf_validate`, `shelf_info`.
- Существующие полки приводятся: `main-memshelf` (тогда `sqst-memshelf`), `unevie-shelf`,
  `homelab-shelf` получают `shelf.yml` и проходят `shelf_validate`.
- docshelf-mcp объявляется reference-реализацией; несоответствия спеку
  чинятся на той стороне (или спек уточняется — v0 описателен).

**DoD:** одна и та же полка подключена к **двум разным MCP-клиентам**
(Claude Code + минимум один сторонний, например ChatGPT-клиент с MCP) и
оба читают/пишут через одинаковые инструменты. `shelf_validate` зелёный на
трёх полках владельца. Это и есть проверяемое «память переносима».

**Первая польза:** `shelf_validate --ci` сразу встаёт advisory-стадией в
shelf-репо (связь с пакетом 04).

**Статус M0 (2026-07-15):** спек, engine, MCP/CLI, тесты — готово.
Кандидаты `shelf.yml` для трёх полок лежат в `docs/adoption/` и проходят
`shelf_validate --ci --manifest` по живым клонам (exit 0, три из трёх);
**коммит `shelf.yml` в сами shelf-репо — действие владельца** (репо полок
read-only для агентов, изменения не применены). Остальные гейты владельца:
создание репо `ignatenkofi/shelf-spec` (issue-черновики оформляются после
него), второй MCP-клиент из DoD, включение advisory-CI в полки
(`docs/advisory-ci.md`).

## M1 — мульти-агентный базис

- `agents.yml`: реестр агентов, зоны (категория × r/rw), самодекларация
  идентичности.
- Provenance-штампы на каждую запись (расширение ledger-механики).
- Advisory-леазы: `lease_claim/release/status`.
- Конвенция «ветка-на-агента/сессию», слияние через PR; линт нарушения зон
  при мёрже.

**DoD:** два агента (для начала — два Claude-агента в разных сессиях, затем
разные вендоры) параллельно пишут в разные зоны одной полки; мёрж через PR;
provenance показывает, кто что написал; попытка записи вне зоны ловится
линтом.

**Гейт перед M1:** пере-проверка ландшафта (mem0/OpenMemory и др.) — ниша
«читаемая git-native память» должна оставаться пустой; иначе — сузить скоуп
до мульти-агентного слоя поверх чужого store.

## M2 — политики и роли

- `policy_check`: прогон политик полки перед фиксацией; первый policy-агент —
  `pii_verify` пакета 02 (тот самый «Lumo-сценарий»: аудитор с read-all).
- Двухплоскостной enforcement: сервер отказывает в записи вне зоны;
  CI-линт полки проверяет мёржи.
- Quarantine-механика: контент от агента без provenance / вне зоны попадает
  в карантин-категорию до ревью.

**DoD:** полка в режиме `multi` с ≥2 агентами и policy-агентом; запись с PII
блокируется гейтом; нарушение зоны не проходит CI.

**Гейт перед M2:** опыт эксплуатации M1 на собственных полках (аналог
недельного memshelf-эксперимента).

## M3 — опционально, по потребности

- Живая конкурентность (локи/очереди в сервере) — только если git-native
  окажется тесен на практике.
- Import-адаптеры вендорской памяти (экспорт из ChatGPT memory и т.п.) —
  ADR-0006 держит их вне ядра.
- Мост к агент-протоколам общения (A2A и др.): messaging + shared state.
- Криптографическая идентичность агентов (подписи записей).
- shelf-spec v1 — публичная стабилизация формата (semver, публикация).

## Вне скоупа

- Векторный поиск/эмбеддинги как часть ядра (можно поверх, отдельным
  инструментом).
- Синхронизация вендорских памятей в обе стороны (ADR-0006).
- Оркестрация агентов (кто когда работает) — координация идёт через саму
  полку (blackboard) и решения пользователя.

## Ядро позиции

Категория «memory MCP» переполнена. Платформенная память есть у Anthropic
(memory tool в API, память claude.ai, авто-память Claude Code, референсный
memory-сервер с графом знаний) и у десятков сторонних проектов. Все они
отвечают на вопрос «как хранить и подмешивать».

Незанятая территория — три вопроса, на которые платформенные решения
не отвечают **по построению**. Это и есть территория полок.

### 1. Что заслуживает хранения (селекция)

Ценность памяти — отношение сигнал/шум, а не объём. Хранить итоги:
решение + отклонённые варианты с причинами, а не транскрипты и логи.

Направления усилий:
- механика курирования: запись — явный финальный шаг сессии, не поток;
- устаревание и забывание как first-class механизм: TTL, ревизии,
  вытеснение. Memory rot проектируется, а не разгребается;
- гранулярность: атом памяти — решение с контекстом, не документ.

### 2. Кому принадлежит (ownership)

Память — данные пользователя, не платформы. Отсюда требования:
- self-hosted по умолчанию;
- переносимость: любой MCP-клиент, никакой привязки к вендору;
- инспектируемость: открытая схема, человекочитаемое хранение,
  экспорт без потерь.

Платформенная память привязывает к платформе; полка переезжает вместе
с пользователем. Это позиция, а не фича — и платформам она недоступна
по определению.

### 3. Как доверять (provenance и верификация)

У каждой записи — происхождение: кто/что создало, на основании чего,
когда. Связка с exp-mcp: хранить воспроизводимое (эксперимент, проверку),
а не только заключение; федеративная верификация — способ доверять чужим
полкам. Формула: память, которой можно доверять, потому что её можно
перепроверить.

## Архитектурный фрейм: pull vs push

- **Push** — платформа заранее решает, что релевантно, и вкладывает
  выжимку в контекст. Модель не выбирает.
- **Pull** — модель распознаёт потребность и запрашивает сама.

Почему pull:
- масштабируется с ростом памяти: в контексте не лежит всё подряд;
- даёт модели агентность над собственной памятью;
- диктует дизайн API: запросные примитивы (поиск, выборка по связям)
  важнее дампов.

Это фрейм и для питча, и для проектирования tool surface. Следствие:
surface узкий, описания тулов короткие — definitions платятся в каждом
сообщении каждого подключённого клиента.

## Каналы выхода

Порядок — по отдаче. Холодное письмо в Anthropic — не канал: хорошие
серверы замечают через экосистему, не через inbox.

### 1. Англоязычный текст

Habr не дотягивается до MCP-сообщества и до Anthropic. Нужны:
- README на английском с тезисом позиции — не «memory server»,
  а pull vs push + ownership + provenance;
- англоязычный пост (dev.to, собственный блог) — переработка статьи
  про MemShelf, которая уже в подготовке.

Английская версия важнее второй русской.

### 2. Официальный MCP Registry

registry.modelcontextprotocol.io — реестр при участии Anthropic, GitHub,
PulseMCP, Microsoft. Метареестр: хранит метаданные, сам пакет живёт
в npm/PyPI/etc. Первичный источник истины для клиентов и суб-реестров —
публикация делает сервер находимым во всей экосистеме.

Механика:
- `server.json` по официальной схеме (`$schema`), версия совпадает
  с версией опубликованного пакета;
- namespace при GitHub-аутентификации: `io.github.<org>/<server>`;
- для пакета в npm/PyPI — маркер `mcp-name` в README, совпадающий
  с именем из `server.json` (можно в HTML-комментарии);
- публикация через `mcp-publisher` CLI; гайд:
  репозиторий modelcontextprotocol/registry →
  `docs/guides/publishing/publish-server.md`.

Практично: задачу публикации можно отдать Claude Code — в гайде лежит
готовый промпт со ссылками на publish-server.md и github-actions.md;
автоматизация через CI предпочтительнее ручного флоу.

### 3. Discussions в организации modelcontextprotocol

Когда из полок вырастет мысль протокольного уровня — например,

Читают мейнтейнеры, включая людей из Anthropic.

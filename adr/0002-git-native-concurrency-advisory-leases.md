# ADR 0002: Git-native конкурентность + advisory-леазы (не lock-сервер, не CRDT)

## Статус

proposed

## Контекст

Главная идея пакета — несколько агентов (в т.ч. разных вендоров)
одновременно работают над общей памятью. Нужна модель совместной записи.
Требования: не потерять свойство «память = просто git-репо» (оно же —
механизм переносимости из ADR-0001), аудируемость слияний, отсутствие
единой точки отказа.

## Решение

- Каждый агент/сессия пишет в **свою ветку**; слияние — через PR;
  арбитр — человек или policy-агент (M2).
- **Advisory-леазы** в `agents.yml`: «агент A держит категорию X до T».
  Леаза — сигнал координации, не замок: честность по договорённости,
  нарушение ловится линтом при мёрже.
- Оптимистическая конкурентность: конфликт = git-конфликт, разрешается
  на ревью, как в коде.

Выбор зафиксирован владельцем 2026-07-15 (из трёх предложенных моделей).

## Альтернативы

- **Stateful lock-сервер (живые локи в MCP-сервере).** Истинная
  одновременность, но появляется сервис-который-должен-жить: SPOF, теряется
  «память = репо», усложняется multi-vendor доступ (все клиенты должны
  ходить в один сервер). Отклонено для M0–M2; возможен в M3, если git-native
  окажется тесен на практике.
- **CRDT / безлоковый мёрж.** Автослияние без конфликтов — технически
  красиво, но тяжело для markdown-семантики (смысловые конфликты CRDT не
  решает) и избыточно для реального масштаба (агентов — единицы). Отклонено.

## Последствия

Реального «в одну секунду в один файл» нет — и не нужно: рабочая
гранулярность — категория/зона, а асинхронная модель совпадает с тем, как
владелец реально работает (PR-циклы). Слияние памяти получает тот же
ревью-процесс, что и код, — это фича: memory-review как практика.
